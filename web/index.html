Other scenarios

Standalone first, plug-in second

The simulator core has no screen and no files of its own. It takes one JSON request and returns one JSON response, so the same code runs as this page, from a command line, behind a small local web service, or inside a larger tool. Only the thin adapters around it change.

Advice only. Every output goes to a named person. The engine has no write path to equipment.

What this is and is not

What it is. A showcase of the Predict, Prescribe, Prove method for haul and crusher flow on a small, notional pit: one pit with four fronts, one crusher, one ROM pad, one waste dump and two truck fleets. A failure model sets breakdown rates, a linear program chooses tonnes and trucks per front, and a discrete-event simulation tests the plan with random breakdowns, loading and dumping times, queues and shift changes.

What it is not. It is not calibrated to any site, it is not an industrial product, and its figures are not forecasts. Every parameter is a labelled assumption to be replaced with client data. The simulation does not model loader breakdowns, road interaction between trucks, blasting, weather other than a speed cut, or driver behaviour.

Reading the result. The gain shown is the fall in cost per plan-equivalent tonne at the same fleet cost, where plan-equivalent tonnes are limited by the scarcer of ore and waste. Raw tonnes moved are similar under both dispatch modes in the base case. The optimiser-guided mode mainly holds the planned ore-to-waste mix.

Method sources. The optimise-then-simulate pairing follows a published Genoa and Vale presentation on a coal mine in Mozambique. The failure-risk step is our addition. Delay terms in the linear program are calibrated from simulated queue times, which is our design choice and not their published method.
